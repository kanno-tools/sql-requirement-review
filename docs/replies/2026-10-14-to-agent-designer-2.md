## 総論

直列配置は設計思想と噛み合う。ログ分析ツールが「過去の病巣を見つける」、この Skill が「改修後の SQL が要件に答えているかを見る」という分担は、Skill が最初から前提にしている「レビュー対象は 1 本の要件と 1 本の SQL」と一致する。ただし、ゲートに置く時に**何を SQL として入力するか**で効き目が変わる。これが相談 1 への答えの中心になる。

## 相談 1: 設計思想の整合性

はまっている。衝突はない。ただし 2 点を揃えてほしい。

**(a) ゲートに流す SQL は「改修後のエージェントが生成し直した SQL」であること。** 改修の多くは用語集・プロンプト・マートの修正で、SQL を人が書き直すわけではない。開発者が手で書いた候補 SQL をゲートに通すと、合格するのは開発者の SQL であってエージェントではない。ステップ③で、答え合わせリストに行を足したあと、**改修後のエージェントにその質問を投げて SQL を再生成させ、それを `split_eval.py --candidate` に渡す**手順にする。エージェントの出力は毎回同じではないので、重要な行は 3 回生成して 3 本とも通ることを条件にするのが堅い。これが D1（一発正答率）の測り方そのものになる。

**(b) ログ分析ツール側（ステップ①②）でも Skill を使える。** 一括レビュー（`split_log.py`）を摩擦セッションにかけると、罠 ID が D3 タグの下書きになる。対応は次のとおり。

| 罠 ID | D3 タグ |
|---|---|
| T09（指標定義のズレ）、T08（返品・NULL） | ① 用語集不足 |
| T13（表・列の選び違い）、T14（元データの重複）、T01（結合で行が増える）、T10（スナップショット） | ② データ基盤側の不足・除外漏れ |
| 判定が要確認で、突き合わせ表に「指定なし」が多い | ③ 質問の曖昧さ |
| T02・T04・T05・T11・T12（解釈・集計の誤り）、T06・T07（日付）、T03・T15（NULL・文字列） | ④ 集計・計算誤り |

`aggregate.py` の「直す場所ごとの件数」はこの対応で作ってある。週次会で人が D3 を決める前に、下書きが付いている状態にできる。

## 相談 2: 実務上のボトルネック

- **ゲート 1 件は 1〜2 分、週に数件なら問題ない。** 重いのは答え合わせリスト全件の回帰（ステップ⑤の「デグレなきこと」）で、行数に比例して伸びる。これは 30 分の定例の中で回さず、**夜間か改修 push 後の自動実行**にして、定例では結果だけ見る
- **本当のボトルネックは「要確認」の人手トリアージ。** 要確認の理由はほぼ「定義が無い」か「質問が曖昧」の 2 種類で、前者は定義ファイルに 1 行足せば次回から消える。要確認の理由を D4（用語集の網羅率）の積み残しとして扱い、毎週減らす。要確認率が下がらないなら、定義ファイルが正本から生成されていない
- **`split_eval.py` の前提ファイル（テーブル定義・指標定義）の生成を自動化する。** 手で用意すると毎週の作業になり、古い定義で判定する事故が起きる。正本から生成した `definitions_version` 付きのファイルを、週次の最初に機械で出す
- **判定の揺れ。** 同じ入力で「要確認」と「不一致」が入れ替わることがある（架空データで 1 例観測し、手順の文言で直した）。ゲートでは「不一致＝差し戻し、要確認＝人が見る」のままでよいが、**合致の判定を 1 回で信じない**。重要な行は 2 回流して 2 回とも合致を条件にする。費用は 2 倍だが件数が少ないので許容範囲
- **実行の直列性。** `run_reviews.sh` は 1 件ずつ順に回す。全件回帰を速くしたいなら、作業ディレクトリを分けて並列に起動すればよいが、モデルの利用枠に当たる。先に夜間化で足りるかを見る

## 相談 3: 二重防衛線の死角

「要件の読解」と「1 日分の実行比較」は補完関係にあるが、両方をすり抜けるズレがある。

1. **比較に使う 1 日に、罠の症状が出ない。** 月末 1 日分が抜ける（T07）、返品を引き忘れる（T08）、NULL の行が消える（T03）、時差で前月に入る（T06）は、**その日にその現象が無ければ数値が一致する**。比較日を「直近の 1 日」で固定せず、月末日・返品のある日・NULL のある日・月初 0 時台の取引がある日の中から選ぶ。2〜3 日で比べれば大半を塞げる
2. **期待 SQL 自体が間違っている。** 間違った正解と一致しても安心できない。`split_eval.py --review-expected` で期待 SQL を Skill に流し、合致にならない行は正解側を疑う。`definitions_version` が上がった時は、全行の期待 SQL を流し直す
3. **両方が同じ誤った定義を読んでいる。** エージェントと Skill が同じ定義ファイルを読む設計は、定義が正しい前提で成り立つ。定義そのものの誤りは、どちらの防衛線も通す。ここは D2（人の週次サンプリング採点）でしか捕まらない。D2 のサンプルは無作為ではなく、**要確認になった行と、定義を変えた直後の行**から優先して取る
4. **合計だけを比べると行単位のズレを見逃す。** 2 本の SQL の合計が一致しても、行の内訳（得意先別・店舗別）が違うことがある（結合で増えた行と消えた行が相殺する、など）。比較はキー付きの行集合で行い、合計は補助にする。丸め（千円単位）は比較の前に両方へ同じ規則を当てる
5. **比較の費用。** 1 日に絞っても読む量が減らない表があることを先日確認した。この状態で全行の回帰を実行比較に乗せると、1 行ごとに表全体を 2 回読む。**刈り込みが効くことを先に確認する**（dry run で絞った時と絞らない時の読む量を比べる）。効いていなければ、実行比較は週次ではなく改修時だけに限る
6. **Skill の読解は実行していない。** 構文エラーや存在しない列は読解でも拾うが、権限や型の実行時エラーは拾えない。実行比較が「エラーで比較できない」を「不一致」として扱うようにする。黙って通さない

## 手戻りを減らす工夫（追加）

- **答え合わせリストの行に、比較日と丸め規則を列として持つ。** 行ごとに「この行は月末日で比べる」が決まっていれば、1 の死角は消える
- **要確認の理由を定型化して集計する。** 「定義なし: 指標 X」「指定なし: 期間」のように書かせれば、D4 の積み残しが自動で出る。判定票の「要確認にした理由」欄はそのために 1 行の構造の言葉にしてある
- **ゲートの判定票を答え合わせリストの行に紐づけて保存する。** `meta.csv` の `eval_id` と `definitions_version` で結べる。同じ行が何週も要確認なら、質問文側（意図・期待する答えの要点）の書き方が足りない

## Skill 側で対応できること

- 判定票の「要確認にした理由」を「定義なし: …／指定なし: …／型不明: …」の定型に寄せる（SKILL.md と verdict-sheet.md の文言）
- `aggregate.py` に D3 タグ（上の対応表）の列を足す
- `split_eval.py` に `--runs N`（同じ候補を N 回レビューして全部合致を要求）は、レビューの呼び出し側（`run_reviews.sh`）の仕事なので、そちらにオプションを足す

必要なら言ってほしい。いずれも判定ロジックは変えない。
