# 連携打診への回答（2026-10-14）

使う環境側でエージェント育成基盤を設計している担当から、この Skill を「改修 SQL のデプロイ前 QA ゲート」として使いたいという打診と、3 つの論点を受けた。以下はその回答。固有名は書かない。

## 総論

3 点とも設計思想と矛盾しない。①と③は、この Skill の「置いた環境だけで動く。定義の正は別にあり、Skill はその写しを読むだけ」という前提そのもの。ただし末尾の「4」で前提を揃えたい事項がある。

## 論点①: 外部定義の動的注入

賛成。すでに半分できている。

- 一括レビュー（`scripts/split_log.py`）には `--schema <path>` があり、テーブル定義を各レビュー入力に埋め込んでいる。同じ形で **`--definitions <path>`** を足し、指標定義表を各入力の「## 指標定義」節として埋め込む。SKILL.md は「入力に指標定義があればそれを `references/metric-definitions.md` より優先する」と読むようにする
- 単発レビューは、依頼ファイルに「## 指標定義」節を書くか、1 行の指示に「定義は @definitions.md を優先」と添えれば同じ効果になる

設計上の要点は注入の仕組みより **「定義ファイルは 1 つで、SQL を書くエージェントとレビューする Skill の両方が同じものを読む」** こと。別々の定義を読めば、レビューは「エージェントの誤り」ではなく「定義の食い違い」を検出してしまう。育成基盤が持つセマンティック定義（クリーンマートの除外条件、店舗属性の補正など）を正本にし、エージェントのシステムプロンプトと Skill への注入ファイルの両方をそこから生成するのが望ましい。

除外条件は、Skill の手順 1 でいう「絞り込み」要素に当たる。定義ファイルに「売上＝除外後」と明記されていれば、除外を忘れた SQL は突き合わせ表の「絞り込み」で不一致になる。書かれていなければ「指定なし」として確認質問に回るだけで、検出はされない。**除外条件は指標の定義の一部として定義ファイルに書く**のが前提。

## 論点②: 答え合わせリスト（eval_set.csv）との接続

スコープに馴染む。ただし 2 つの検査を分けて考える。

- **要件に対する検査**（この Skill の仕事）: 候補 SQL が `user_question`＋`prompt_intent`＋`expected_output_definition` に答えているか。期待 SQL は見せない。見せるとレビューが期待 SQL に引きずられ、「要件に答えているか」ではなく「期待 SQL と似ているか」を判定してしまう
- **期待 SQL との一致検査**（この Skill の仕事ではない）: 候補と `expected_sql` を同じ 1 日分のパーティションで実行して結果を比べる。決定的で安く、数値の一致を保証できる。このリポジトリの `tests/check_cases.py` が架空データでやっているのと同じこと

接続は入力アダプタ 1 本で足りる。`scripts/split_eval.py --csv eval_set.csv --id 105 --candidate fixed.sql` のような形で、CSV の 3 列から「## 要件」を組み立て、候補 SQL を「## SQL」に置き、`--definitions` と `--schema` を埋めて `req105.md` を出す。あとは既存の `run_reviews.sh` と `aggregate.py` がそのまま使える。判定票の `id` を eval_set の `id` に合わせれば、週次の振り返りで「どの ID が不一致か」が集計に直接出る。

提案: eval_set に `definitions_version`（どの定義ファイルで正解を作ったか）の列を持つ。定義が更新されると過去の期待 SQL が古くなり、その区別が無いと「Skill の誤検出」と「定義の更新」を見分けられない。

## 論点③: 機密分離

方針に賛成。ただし事実を 1 つ訂正する。公開リポジトリの雛形には実プロジェクト名・マート名は入っていない（確認済み）。実名が入っているのは、使う環境で記入したコピーで、それは `~/.gemini/skills/sql-requirement-review/references/` にあり、git の管理外。したがって `skip-worktree` の出番はない。Skill を置くディレクトリは git の checkout ではない。

実質的な防波堤は 2 つ。Skill を使う VM から公開リポジトリへ直接 push しない（push する場合は main を保護し、ブランチ止まりにして人が diff を見てからマージする）。レビュー対象のファイルと記入済みの定義表を clone の中に置かない。

組織内で定義入りの Skill を配布したいなら、公開リポジトリを上流にした組織内フォークに定義ファイルを置くのが筋。上流は雛形のまま、フォークが `references/metric-definitions.md` と `schema.md` を持つ。更新は上流から取り込む。

## 4. 揃えてほしい点

1. **判定の 3 値と「正答率」の対応を決める。** Skill は合致／要確認／不一致を返す。要確認を正答に数えるか誤答に数えるかで数字が変わる。推奨は、要確認を別枠で数え、ゲートでは「不一致＝差し戻し、要確認＝人が見る、合致＝通す」
2. **ゲートに置く前に、その環境のデータで Skill の精度を測る。** eval_set の `expected_sql` を Skill に流せばすべて「合致」になるべきで、過去に数字が狂った SQL を流せば「不一致」になるべき。架空データでは罠 15 本・正しい SQL 10 本で誤検出ゼロだが、実環境の表と用語での数字はまだ無い。`run_reviews.sh` を eval_set 由来の入力に回すだけで測れる
3. **実行確認（手順 5）はゲートでは切る。** 1 日に絞っても読む量が減らないビューがあることを確認している。読解だけで判定でき、BigQuery の費用はゼロになる。期待 SQL との結果比較を別途行うなら、そちらでパーティション 1 日分に固定する
4. **テーブル定義と指標定義は、SQL が触る表の分だけ注入する。** 全表分を毎回入れると 1 件あたりの入力が増える。`split_log.py` 側で SQL から表名を拾って絞る改修は小さい

## 対応予定（Skill 側）

- `--definitions` の追加と、SKILL.md の優先順位の明記
- `split_eval.py`（eval_set からの入力アダプタ）
- `--schema` / `--definitions` の表名による絞り込み

いずれも Skill の判定ロジックは変えない。
