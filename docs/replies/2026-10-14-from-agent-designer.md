## 論点②: 答え合わせリスト（eval_set.csv）との接続

2つの検査を分離する整理に全面的に同意する。

- **要件に対する検査（当Skillの担当範囲）**:
  候補SQLが「質問文＋意図＋期待する答えの要点」を満たしているかを純粋に読解・監査する。期待SQLは入力アダプタ経由で見せない仕様とする。
- **期待SQLとの一致検査（別スクリプトの担当範囲）**:
  候補SQLと期待SQLを同一の1日分パーティションで実行し、集計結果の一致を決定論的かつ低コストに検証する。
- **入力アダプタ（`split_eval.py`）の新設**:
  作成方針に合意・感謝する。
- **`definitions_version` の追加（提案の受け入れ）**:
  答え合わせリストの列仕様に `definitions_version`（どの定義版数に基づいて正解を作成したか）を直ちに追加する。これにより、定義改訂に伴う期待SQLの陳腐化と当Skillの検出精度を明確に区別して運用する。

※参考：当方で運用予定の答え合わせリスト（`eval_set.csv`）の列構成:
`id, user_question, prompt_intent, expected_output_definition, expected_sql, source, added_date, definitions_version, last_result`

## 4. 揃えてほしい点への回答

提示された4つの要請事項について、以下のとおり対応・確定する。

1. **判定の3値と「正答率」の対応**:
   **推奨案を採用・確定する。**
   - 【合致 (PASS)】: ゲート通過（次のステップである期待SQLとの決定論的一致検証、および回帰テストへ進行）。
   - 【要確認】: ゲート保留・人手トリアージへ回す（開発者が内容を確認し、定義の曖昧さかSQLの問題かを判断）。正答率の母数からは一旦別枠として扱う。
   - 【不一致 (FAIL)】: ゲート遮断・即時差し戻し（本番へのデプロイを物理的に拒絶）。
2. **ゲート配備前の実環境データでのSkill精度測定**:
   **了解。**
   ゲートへの本番配備に先立ち、当環境の過去の異常SQL（除外条件漏れ、意図違い、迷走ログ）および確定済みの期待SQLを抽出し、当Skillに流して「期待SQLが100%合致になるか」「過去の異常SQLが確実に不一致として検出されるか」を事前に測定・検証する。
3. **実行確認（手順5）のゲート除外**:
   **合意。**
   CI/CD的なゲート運用においては、手順5の実行確認（ドライラン）はOFFとし、静的読解・突き合わせのみに限定する。これによりBigQueryスキャン費用ゼロで判定を完了させる。数値の完全一致は、前述の「別スクリプトによる1日分パーティション比較」で担保する。
4. **テーブル定義と指標定義の対象テーブル限定注入**:
   **合意。**
   入力トークン抑制とコンテキスト鮮度維持のため、SQLまたは要件が触れる対象テーブルの定義のみを絞り込んで注入する方針とする。`split_log.py` / `split_eval.py` 側での自動絞り込み改修を歓迎する。
