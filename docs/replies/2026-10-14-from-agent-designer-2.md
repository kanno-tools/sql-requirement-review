## 1. エージェント成長サイクルの全体構造

当方では、現場（非エンジニアの営業組織）が商談準備で自律的に利用するデータ分析エージェントを育成している。エージェントを「作って終わり」にせず、現場の利用から生まれるログを原料にして自走的に賢く育てるサイクルを以下の2大指標体系と因果ループで設計している。

### (1) 指標体系（S指標 ＆ D指標）
* **営業定着度（S指標 / 現場の利用実態）**:
  - `S1`: アクティブ利用人数（週次）
  - `S2`: 重要商談前の事前利用率（業務への組み込み度）
  - `S4`: 質問タイプの高度化構成比（記述的［実績確認］➔ 診断的［要因深掘り］➔ 予測・処方的［施策提案］）
  - `S5`: 対話深度（複数往復・深掘り壁打ちの比率）
* **エージェント品質度（D指標 / システムの客観性能）**:
  - `D1`: 一発正答率（目標: 80%以上。複数回のリトライや迷走なく1回のSQL実行で完結した割合）
  - `D2`: 業務正答率（人間による週次サンプリング採点）
  - `D3`: 摩擦原因分類タグ（①用語集不足、②データ基盤側の不足・除外漏れ、③質問の曖昧さ、④集計・計算誤り、⑤インフラ遅延・その他）
  - `D4`: 業務用語集の網羅率
  - `D5`: 低速・高スロット消費クエリ率（インフラ負荷）

### (2) 因果ループ構造（Hamel Husain / OpenAI の知見に立脚）
```
                  【エージェント自走育成の因果ループ】

     ┌────────────────────────────────────────────────────────┐
     │                                                        │
     ▼                                                        │
［品質度 D の最低防衛線］（D1: 正答率 80%以上）                │
     │                                                        │
     │  信頼の獲得（「嘘の数字を出さない」保証）              │
     ▼                                                        │
［営業定着度 S の発生］（S1: 利用人数、S2: 商談前利用率）      │
     │                                                        │
     │  実業務での活用（未知の質問・複雑な商談文脈の投入）    │
     ▼                                                        │
［生ログ・摩擦の発生］（聞き返し・迷走SQL・諦め離脱）         │
     │                                                        │
     │  ログ分析ツールによる抽出 ＆ 週次での処方箋確定        │
     ▼                                                        │
［品質度 D の真の向上］（D2: 業務正答率向上、D4: 用語網羅）    │
     │                                                        │
     └────────────────────────────────────────────────────────┘
```
* **初期**: 「品質（D1 80%以上）が定着（S）の絶対防衛線」である。現場は商談に使う数字を求めており、一度でも数字の誤り（除外条件漏れや集計キー違い）を経験すると二度と使わなくなる。
* **展開期**: 「定着（S）がなければ、品質（D）の伸び代が止まる」。開発室の机上テスト（模範的な質問）だけでは現場の実利用分布を網羅できない。現場に使われることで初めて未知の失敗ログ（摩擦）が溜まり、それを改修することが品質向上の原料となる。

## 2. 週次PDCAパイプラインにおける貴Skillの配置

毎週30分の定例振り返りにおいて、以下の実務パイプラインを回す。ここで貴Skillを**「ステップ④：デプロイ前QA監査ゲートキーパー」**として位置付けている。

```
┌────────────────────────────────────────────────────────────────────────┐
│               エージェント自走育成 ＆ 品質保証パイプライン              │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │
  ①【異常検知】                    ▼
  ログ分析ツールが日々の対話ログから「摩擦セッション（複数試行・離脱）」を客観抽出
                                   │
                                   ▼
  ②【原因特定 ＆ 処方箋確定】
  週次会にて摩擦カルテを確認し、人間（担当者）がD3タグと改修方針を決定
  （用語集の追加 / プロンプト制約の追加 / データマートの改修）
                                   │
                                   ▼
  ③【開発者による改修 ＆ 評価事例化】
  開発者が修正を施し、該当の質問文・意図・期待要点を答え合わせリスト（`eval_set.csv`）へ1行追加
                                   │
                                   ▼
  ④【品質保証ゲート（デプロイ前QA監査）】 ★ここで貴Skillを発動
  ┌──────────────────────────────────────────────────────────┐
  │  Skill: sql-requirement-review                           │
  │  ・scripts/split_eval.py で入力 Markdown を生成          │
  │  ・要件の分解（6要素） ➔ SQLの逆翻訳 ➔ 突き合わせ         │
  │  ・15大罠チェック（T01〜T15全件監査: 除外漏れ、結合爆発等）│
  │  ・判定: 【合致 / 要確認 / 不一致】                      │
  └──────────────────────────┬───────────────────────────────┘
                             │
            ┌────────────────┴────────────────┐
            │ [合致 (PASS)]                   │ [要確認 / 不一致 (FAIL)]
            ▼                                 ▼
  ⑤【決定論的一致検査 ＆ 回帰テスト】          手戻り修正（本番反映を物理遮断）
  ・候補SQLと期待SQLを同一1日分パーティションで
    実行し、集計値の一致を確認
  ・eval_set 全件を実行しデグレなきことを実証
            │
            ▼
  ⑥【本番環境へ安全反映】
```

### 役割分担の整理
* **ログ分析ツールの役割**: **「過去の病巣を見つける（診断・検知）」**。生ログから現場の困りごとを客観抽出する。
* **貴Skillの役割**: **「未来の再発・デグレを防ぐ（監査・予防）」**。改修されたSQLが業務要件と合致しているか、別の罠を踏んでいないかを客観的に査定し、粗悪な修正が本番へ混入することを防ぐ。

## 3. 貴Skill管理側に伺いたい点（相談・質問）

上記のエージェント成長サイクルおよびQAパイプラインを踏まえ、以下の3点について見解やアドバイスをいただきたい。

1. **設計思想の整合性について**:
   ログ分析ツール（過去の摩擦検知）と貴Skill（改修後SQLの要件監査ゲート）をこのように分離・直列配置する構成は、貴Skillの設計思想から見て見事にはまっているか？ 無理な結合や思想の衝突はないか？
2. **実務運用上のボトルネックについて**:
   週次30分の振り返り〜週内改修という実務テンポにおいて、`split_eval.py` ➔ レビュー実行 ➔ トリアージという流れで運用する際、実効性・負荷の観点でボトルネックになりそうな点はあるか？
3. **二重防衛線（要件検査 ＋ 1日分パーティション数値突合）の死角について**:
   「当Skillによる要件読解監査」を通過した後に「同一1日分パーティションでの期待SQLとの実行結果比較」を行う二段構えを予定している。この構成において見落としがちな罠や、さらに手戻りを減らすための工夫があれば教えていただきたい。
