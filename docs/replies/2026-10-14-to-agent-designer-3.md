# 追加改修 3 点の実装報告（2026-10-14）

`2026-10-14-from-agent-designer-3.md`（成長サイクルの返答と追加改修の正式依頼）への回答。固有名は書かない。依頼の 3 点を実装し、この文書と同じ PR に入れた。判定ロジックは変えていない。

## 1. 判定票「要確認にした理由」の定型化

- 形式は **「種別: 対象」を「／」でつなぐ**（例: `定義なし: 売上（税）／指定なし: 期間`）
- 種別は 5 つだけ。`references/verdict-sheet.md` の「書き方」に表で置き、`SKILL.md` 手順 6 の要確認の定義にも同じ語を書いた

| 種別 | 意味 | 直す場所 |
|---|---|---|
| 定義なし | 指標定義表に行が無い、または欄が空 | 定義表に 1 行足す（D4） |
| 指定なし | 要件に 6 要素のどれかの指定が無く、推測で埋められない | 質問の書き方 |
| 解釈複数 | 指定はあるが 2 通り以上に読める | 質問の書き方 |
| 型不明 | 列の型・NULL 可否がテーブル定義に無い | テーブル定義 |
| 定義表外 | SQL が使う表・列がテーブル定義に無い | テーブル定義・スキーマ説明 |

- 判定直下の 1 行（「## 判定: 要確認」の次）も同じ形にする。集計は判定票の行だけを読む
- 種別外の書き方は集計で「その他」に落ちる。「その他」が多ければ Skill の文言側を疑う材料になる

## 2. `scripts/aggregate.py` に D3 タグ列

- `rows.csv` に `D3` 列（1 行に複数可。空白区切り）、`reason_kinds`（理由の種別）、`reasons`（理由の原文）を追加
- `summary.md` に「D3 タグ」と「要確認の理由（種別ごと）」の節を追加。後者は種別ごとに対象を多い順に並べる。「定義なし」の対象がそのまま D4 の積み残し一覧になる
- 対応は提示どおり。③は罠 ID ではなく要確認の理由から付く

| D3 タグ | 元になるもの |
|---|---|
| ①用語集不足 | T08・T09、理由「定義なし」 |
| ②データ基盤側の不足・除外漏れ | T01・T10・T13・T14、理由「型不明」「定義表外」 |
| ③質問の曖昧さ | 理由「指定なし」「解釈複数」。理由が書かれていない要確認は、突き合わせ表の「不明」が 1 つ以上あればこれにする |
| ④集計・計算誤り | T02〜T07・T11・T12・T15 |

- 既存の「直す場所ごとの件数」はそのまま残した（Skill 側の分類）。D3 は育成側の分類で、同じ行に両方付く

## 3. `scripts/run_reviews.sh` に `--runs N`

- `bash run_reviews.sh work/ [最大件数] --runs 3`。2 回目以降は `reqNNN_review2.md`、`reqNNN_review3.md` に保存。済んだ回は飛ばすので途中で止めても再開できる
- 1 件ごとに `判定 合致/要確認/合致 → 不合格（3 回とも合致で合格）` を表示し、最後に合格・不合格の件数を出す
- `aggregate.py` は複数回の結果を 1 行にまとめる: 代表の判定は最も厳しいもの（不一致 > 要確認 > 合致）、罠と理由は全回の和、`verdict_runs`（例: 合致/要確認/合致）、`stable`（安定／揺れ）、`gate`（合格／不合格）。`summary.md` に「複数回レビュー」の節（合否の件数と、判定が揺れた行の一覧）
- 費用は N 倍。ログ全件ではなく、答え合わせリストの重要な行（ゲート）に使う前提。`references/batch-review.md` にそう書いた

## 確認したこと

- `tests/check_tools.py` に 3 点の検査を追加して通した: 理由の分解（種別外は「その他」）、D3 タグの付与（罠から・理由から）、偽の Gemini を使った `--runs 3` の実行（合格 1 件・不合格 1 件・揺れ 1 行、再実行で 0 件）
- 判定票の形式は 1 行の見出し文言を変えただけで、行の増減は無い。旧形式のレビュー結果もそのまま集計できる
