# 罠チェックリスト（v1・15 項目）

T01〜T15 すべて、罠入り SQL と正しい SQL の両方で検出を確認済み。実使用で効かなければ書き換える。

どれも「エラーは出ないのに数字が違う」系。全項目を点検し、該当なしも「該当なし」と書く。
各項目: **見つけ方**（SQL のどこを見るか）／**Alteryx でいうと**／**典型的な被害**。

---

## T01 JOIN での行の水増し
- 見つけ方: JOIN の相手表で、結合キー 1 つに複数行が紐づかないか（1 対多・多対多）。期間で結合する施策・価格表・履歴表は特に要注意。その後に SUM/COUNT していれば水増しが確定する
- Alteryx でいうと: 結合ツールの J 出力の件数が、左入力より増えている
- 典型的な被害: 売上が 2 倍・3 倍に膨らむ。重なる施策が 2 本あれば、同じ売上が 2 回数えられる

## T02 INNER JOIN での欠落
- 見つけ方: `JOIN` / `INNER JOIN` の片側にしか存在しない行を、要件が求めていないか（「全得意先」「目標のある得意先すべて」「実績ゼロも含めて」）。`LEFT JOIN` でも、右表の列を WHERE で絞ると INNER と同じになる
- Alteryx でいうと: 結合ツールの L 出力（結合できなかった左側）を捨てている
- 典型的な被害: 実績ゼロの得意先・店舗が一覧から消え、「全店達成」に見える

## T03 NULL 行の脱落（`<>` / `NOT IN` / `=`）
- 見つけ方: 除外条件 `col <> 'X'`、`col NOT IN (...)`、`col = ...` の列に NULL が入りうるか。NULL の行は条件が真にならず、黙って消える。`NOT IN (サブクエリ)` のサブクエリ側に NULL が 1 つでもあれば、結果は 0 行になる
- Alteryx でいうと: フィルターツールで [region] != "関東" とすると、Null の行は F 側に落ちる
- 典型的な被害: 「関東以外」の集計から、地域未登録の得意先が消える

## T04 COUNT と COUNT(DISTINCT) の取り違え
- 見つけ方: 要件の「何を数えるか」（取引件数か、店舗数か、得意先数か、商品数か）と、`COUNT(*)` / `COUNT(col)` / `COUNT(DISTINCT col)` が合っているか。`COUNT(col)` は NULL を数えない
- Alteryx でいうと: 集計ツールの Count と Count Distinct の違い
- 典型的な被害: 「購入店舗数」のつもりが取引件数になり、数倍になる

## T05 WHERE と HAVING の位置
- 見つけ方: 「合計が X 以上の得意先」のように集計結果で絞る条件が WHERE に書かれていないか（行単位で先に絞るので意味が変わる）。逆に、行単位の条件が HAVING にあっても結果は通常同じ（性能の問題）
- Alteryx でいうと: 集計ツールの前にフィルターを置くか、後に置くか
- 典型的な被害: 「1 回 5 万円以上の取引の合計」になり、「合計 5 万円以上の得意先」とは別物になる

## T06 タイムゾーン（BigQuery の既定は UTC）
- 見つけ方: TIMESTAMP 型の列を `DATE(ts)`、`EXTRACT`、`DATE_TRUNC`、日付リテラルとの比較で扱っているか。タイムゾーン指定（`DATE(ts, 'Asia/Tokyo')`、`TIMESTAMP('2026-06-01', 'Asia/Tokyo')`）が無ければ UTC 基準。**JST とは 9 時間ずれ、JST 0:00〜8:59 の取引が前日・前月に入る**
- Alteryx でいうと: 日時ツールで UTC→JST 変換をせずに日付を切り出している
- 典型的な被害: 月初 0 時台の売上が前月に計上される。日別集計の山が 9 時間ずれる
- 注: 列の型が DATE、または JST で保存された DATETIME なら該当しない。型が不明なら確認質問に回す

## T07 期間境界（BETWEEN・月末・未満/以下）
- 見つけ方: `BETWEEN '2026-06-01' AND '2026-06-30'` を TIMESTAMP に使うと、6/30 は 00:00:00 ちょうどまでしか含まれず、6/30 の取引がほぼ消える。`<` と `<=` の違い、月末日（28/30/31 日）の決め打ち、「直近 30 日」と「先月」の取り違えも見る
- Alteryx でいうと: フィルターの日付条件で終端の日を含めているかどうか
- 典型的な被害: 月末 1 日分が抜ける。「先月」のはずが「過去 30 日」になる

## T08 返品・マイナス行・NULL 金額の扱い
- 見つけ方: 数量・金額にマイナス（返品・訂正）がありうるか、それを要件が「純売上（控除後）」と「総売上（控除前）」のどちらで求めているか。`WHERE amount > 0` で返品を消していないか。SUM は NULL を無視し、AVG は NULL を分母から外す
- Alteryx でいうと: フィルターで正の値だけ残しているか／Null を 0 に置換してから平均しているか
- 典型的な被害: 返品を引かずに売上を過大計上する。NULL を含む平均が過大になる

## T09 指標定義のズレ（税込・税抜・定価・実売など）
- 見つけ方: 要件の指標（売上・金額・単価・粗利）が、SQL のどの列・どの計算式に当たるか。`metric-definitions.md` の定義と照合する。**定義が無ければ推測せず、確認質問に回す**。定価 × 数量と実売金額の取り違えもここで見る
- Alteryx でいうと: フォーミュラツールで計算した列が、要件の定義と一致しているか
- 典型的な被害: 定価ベースで売上を出して、値引き分だけ過大になる

## T10 最新スナップショットの選び方
- 見つけ方: 在庫・残高・会員ステータスなど日次スナップショットの表から「現在」「月末時点」を取るとき、最新日を 1 行に絞っているか（`QUALIFY ROW_NUMBER() OVER (PARTITION BY ... ORDER BY 日付 DESC) = 1` など）。`MAX(stock_qty)` のように値の最大を取っていないか。全日付を SUM していないか。PARTITION BY の単位が要件の粒度と合っているか
- Alteryx でいうと: 並べ替え → 一意ツールで最新行だけ残す処理
- 典型的な被害: 在庫が日数分合算されて何倍にもなる。最新ではなく最大値が出る

## T11 ゼロ除算・比率の計算
- 見つけ方: `a / b` の分母が 0 や NULL になりうるか（BigQuery では 0 除算でクエリ全体がエラー）。`SAFE_DIVIDE` で NULL になった行をどう表示するか。比率の平均（行ごとの達成率の平均）と、合計同士の比率（Σ実績 ÷ Σ目標）の取り違え
- Alteryx でいうと: フォーミュラで割り算する前に、分母が 0 の行を IF で分けているか
- 典型的な被害: 全体達成率が、得意先ごとの達成率の単純平均になっている

## T12 ORDER BY 無しの LIMIT・同順位の扱い
- 見つけ方: 「上位 N 件」なのに `ORDER BY` が無い、または並べ替えの列や向き（DESC/ASC）が要件と違う。同点のとき何件出すか（`RANK` と `ROW_NUMBER` の違い）
- Alteryx でいうと: 並べ替えツールを通さずにサンプルツールで先頭 N 件を取っている
- 典型的な被害: 実行のたびに違う「トップ 5」が出る。売上最下位 5 件が出る

## T13 表・列の選び違い（AI 生成 SQL で最も多い）
- 見つけ方: FROM / JOIN の表名と SELECT の列名を、**テーブル定義（データカタログ）と 1 つずつ照合**する。似た名前の表（`sales` と `sales_v2`、日次と月次、生データと集計済み）、似た名前の列（税込と税抜、定価と実売、受注日と出荷日）を取り違えていないか。定義に無い列名が出てきたら、その SQL は存在しない列を推測で書いている
- Alteryx でいうと: 入力データツールで別のファイルやシートを選んでいる
- 典型的な被害: SQL の論理は正しいのに、元が違うので数字が全部違う。要件と SQL を見比べても気づけない
- 注: テーブル定義が無い時は、この項目を「不明」とし、確認質問の先頭に「表 X・列 Y は要件の△△に対応する正しい表・列ですか」を置く

## T14 元データの重複行
- 見つけ方: 事実表（売上・取引・ログ）に同じ取引が複数行入りうるか（再送・訂正履歴・複数システムからの取り込み）。取引 ID で `COUNT(*)` と `COUNT(DISTINCT id)` が違えば重複がある。SQL 側で重複を除く処理（`DISTINCT`、`QUALIFY ROW_NUMBER() = 1`）が無ければ、そのまま合計に乗る
- Alteryx でいうと: 一意ツールを通さずに集計している
- 典型的な被害: SQL は正しく見えるのに、数字が実際より大きい。手順 5 の件数確認で最も見つけやすい

## T15 文字列の一致ミス
- 見つけ方: `WHERE name = '…'`、`IN (…)`、`LIKE '%…%'` の比較で、全角と半角、大文字と小文字、前後の空白、表記ゆれ（「株式会社」の有無・ハイフンの種類）が混ざりうるか。`LIKE '%薬局%'` の部分一致が意図しない行を拾わないか。マスタの ID で絞れるのに名前で絞っていないか
- Alteryx でいうと: フィルターの文字列条件で、トリムや大文字小文字の統一をしていない
- 典型的な被害: 得意先名で絞ると一部の店舗が漏れる。部分一致で別の得意先まで拾う
- 注: T13 との書き分け。要件の言葉に対応する区分列（チャネル・ID など）があるのに名前で絞っているなら T13 が主で T15 は従（両方挙げる）。表・列は正しいが比較の仕方（部分一致・全角半角・空白）が悪いなら T15 だけ。テーブル定義に値の一覧がある区分列を、その値どおりに完全一致で比較しているなら該当なし
